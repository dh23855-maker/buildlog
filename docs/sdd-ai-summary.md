## 1. 목적과 범위

### 1.1 목적
사용자가 이미지나 영상을 저장하면 서버가 내부적으로 OpenAI를 호출해 내용을 요약하고, 그 요약을 자료 정보와 함께 저장·표시한다. 개발자는 `backend/.env`에 **OpenAI 키만 넣으면** 바로 동작해야 한다.

### 1.2 요구사항 추적 (요청 → 설계)

| 요청 | 설계에서 충족하는 방법 | 장 |
| --- | --- | --- |
| (1) 저장하는 순간 내부적으로 OpenAI 호출 | 자료 저장을 확정한 직후 분석을 예약해 백그라운드에서 호출 | 4, 8 |
| (2) 적절한 프롬프트로 이미지·영상 내용 요청 | 한국어 요약 지시문 고정, 영상은 장면 프레임으로 변환 | 6, 7 |
| (3) 너무 비싸지 않은 모델 | 이미지 입력이 되는 mini급 모델, 모델 이름은 설정값, 출력·프레임·횟수 제한 | 6.3, 6.6 |
| (4) 요약을 이미지 테이블에 함께 저장 | `materials`에 `summary` 등 열 추가 (마이그레이션 0004) | 3 |
| (5) 키만 넣으면 작동 | 필수 설정은 `OPENAI_API_KEY` 하나, ffmpeg는 패키지에 포함, 나머지는 기본값 | 5 |

### 1.3 이번 범위 밖
- 영상의 **소리** 분석(음성 인식), 자막 추출
- 요약 수정·직접 편집, 요약으로 검색
- 별도 작업 큐(Celery·Redis 등), 여러 서버로 확장
- 사용자별 월 결제·과금
- 기존 자료의 일괄 자동 재분석 (사용자가 자료별로 "AI 요약 만들기"를 누르는 방식만 제공)

### 1.4 용어
| 용어 | 뜻 |
| --- | --- |
| 분석 | 자료 1건에 대해 OpenAI를 한 번 호출해 요약을 만드는 일 |
| 분석 상태 | `skipped`(안 함) · `pending`(진행 중) · `done`(완료) · `failed`(실패) |
| 프레임 | 영상에서 뽑은 정지 화면(JPEG) |
| 한도 | 사용자 1명이 하루에 시작할 수 있는 분석 횟수 |

## 3. 데이터 설계

### 3.1 `materials` 열 추가 (마이그레이션 `0004`)

| 열 | 형식 | 조건 | 설명 |
| --- | --- | --- | --- |
| `summary` | Text | NULL 가능 | 요약문. 서버가 2,000자로 자른 평문 |
| `analysis_status` | String(10) | 필수, 기본 `skipped`, CHECK(`skipped`·`pending`·`done`·`failed`) | 분석 상태 |
| `analysis_error` | String(40) | NULL 가능 | 실패 코드 (6.5의 표). 사용자용 문장은 코드로 만들어서 보냄 |
| `analyzed_at` | DateTime(timezone) | NULL 가능 | 분석이 끝난(성공·실패) 시각, UTC |
| `analysis_model` | String(64) | NULL 가능 | 요약을 만든 모델 이름 (나중에 품질·비용 추적용) |

- 기존 자료는 마이그레이션 직후 모두 `skipped`이다. 사용자가 "AI 요약 만들기"를 눌러 하나씩 채울 수 있다.
- 체크 규칙 이름: `ck_materials_analysis_status`. SQLite에서도 적용되도록 `op.batch_alter_table`을 쓴다. 기존 `ck_materials_*` 규칙은 유지한다.
- `downgrade`는 추가한 열과 `ai_usage`를 지운다. **요약 데이터가 사라진다**는 점을 주석에 명시한다.

### 3.2 신규 표 `ai_usage` (하루 한도 계산용)

| 열 | 형식 | 조건 |
| --- | --- | --- |
| `user_id` | Integer | 기본 키 일부, `users.id` 외래 키 (`ON DELETE CASCADE`) |
| `day` | Date | 기본 키 일부. **한국 날짜**(Asia/Seoul) |
| `count` | Integer | 필수, 0 이상 |

- 한도를 `materials`의 행 수로 세면 "올리고 분석하고 삭제"를 반복해 한도를 우회할 수 있다. 자료가 지워져도 남도록 **별도 표**에 센다.
- 사용자가 지워지면 함께 지워진다.

### 3.3 모델 코드 (`app/models/material.py`)
- `Material`에 위 열을 추가한다. `analysis_status`의 파이썬 기본값은 `"skipped"`이고 `server_default`도 `'skipped'`로 맞춘다. (Alembic 비교 테스트가 어긋나지 않게)
- `AiUsage(user_id, day, count)`를 `app/models/ai_usage.py`에 만들고 `models/__init__.py`에 등록한다.

## 4. 구조와 흐름 (To-Be)

### 4.1 구성

```
[브라우저]                       [FastAPI 서버]                                [외부]
 MaterialsPage ──POST /api/materials──▶ create_material
   (ai_summary 체크)                       │ ① 파일 저장·DB 확정 (기존 흐름, 변경 없음)
                 ◀── 201 (status=pending) ─┤ ② 분석 예약 ─▶ AnalysisExecutor(스레드 2개)
                                           │                      │
 3초마다 GET /api/materials ──────────────▶│                      ▼
 (pending이 있는 동안만)                    │              run_analysis(material_id)
                 ◀── status=done, summary ─┤               ├ 파일 읽기 / 영상이면 video_frames (ffmpeg 프로세스)
                                           │               ├ 하루 한도 확인·차감 (ai_usage)
                                           │               ├ openai_client ─────────────▶ OpenAI Responses API
                                           │               └ materials에 결과 저장
```

### 4.2 업로드 → 분석 순서

1. 사용자가 "자료 업로드"를 누른다. 화면은 `title`, `memo`, `file`, `ai_summary`를 `FormData`로 보낸다.
2. 서버는 **기존 순서대로** 로그인 확인 → 검사 → 파일 저장 → DB 확정까지 마친다. 여기까지 실패하면 AI와 무관하게 기존처럼 전부 되돌린다.
3. 확정이 성공한 뒤에 분석 상태를 정한다.
   - AI 사용 가능(키 있음) **그리고** 사용자가 요약을 원함 → `pending`으로 저장하고 분석 예약
   - 그 외 → `skipped`
4. 응답은 분석을 기다리지 않고 바로 돌려준다 (201, `analysis_status`는 `pending` 또는 `skipped`).
5. 백그라운드에서 `run_analysis(material_id)`가 실행되어 결과를 저장한다. 화면은 폴링으로 변화를 본다.

> 3번에서 `pending` 표시와 자료 저장을 **같은 트랜잭션**으로 처리한다. 저장은 됐는데 상태 표시가 없는 중간 상태를 만들지 않기 위해서다. 분석 예약(`submit`)은 commit 이후에 한다.

### 4.3 분석 상태 전이

```
            (업로드, AI 꺼짐·미선택)                         (업로드, AI 켜짐·선택)
 [없음] ───────────────▶ skipped                    [없음] ───────────────▶ pending
                          │  POST /analyze                                   │
                          └──────────────▶ pending ◀──── POST /analyze ── failed
                                              │  ▲
                                   성공 ┌─────┘  └─────┐ 실패·중단
                                        ▼                ▼
                                      done            failed
```

| 현재 | 허용되는 일 | 결과 |
| --- | --- | --- |
| `skipped` | 다시 분석 요청 | → `pending` |
| `failed` | 다시 분석 요청 | → `pending` |
| `pending` | 다시 분석 요청 | **거절** (409 "이미 분석 중이에요.") |
| `done` | 다시 분석 요청 | **거절** (409 "이미 요약이 있어요.") — 비용 낭비 방지 |
| `pending` | 서버 재시작 | → `failed` (`interrupted`) |
| `pending` | 자료 삭제 | 결과를 버림 |

상태 변경은 모두 **한 문장의 조건부 UPDATE**(`WHERE id=… AND analysis_status IN (…)` 후 영향받은 행 수 확인)로 한다. 읽고 나서 쓰는 방식은 동시 요청에서 두 번 분석될 수 있어 쓰지 않는다.

## 5. 설정 설계

### 5.1 환경 변수 (`backend/.env`)

| 이름 | 필수 | 기본값 | 설명 |
| --- | --- | --- | --- |
| `OPENAI_API_KEY` | **AI를 쓰려면 필수** | (비어 있음) | OpenAI 키. 비어 있으면 AI 기능만 꺼지고 서버·업로드는 정상 동작 |
| `OPENAI_MODEL` | 선택 | 코드의 기본 상수 (A0에서 확정, 6.3) | 사용할 모델 이름 |
| `AI_DAILY_LIMIT` | 선택 | `30` | 사용자 1명당 하루 분석 횟수 (한국 날짜 기준) |

- `.env.example`에는 **항목 이름과 설명만** 적고 값은 비워 둔다. 실제 키는 코드·문서·Git·답변·로그에 넣지 않는다. (`CLAUDE.md` 규칙 5)
- 키를 넣거나 바꾼 뒤에는 **백엔드를 다시 켜야** 반영된다.

### 5.2 코드 (`app/config.py`)
- `openai_api_key: SecretStr = SecretStr("")` — 출력해도 `**********`로 보이게 한다. 앞뒤 공백과 따옴표를 제거한다. (`DATABASE_URL`과 같은 방식)
- `openai_model: str = ""` → 비면 `DEFAULT_OPENAI_MODEL` 상수 사용.
- `ai_daily_limit: int = 30` (1 이상으로 검사. 잘못된 값이면 기본값으로 돌아가며 시작 기록에 경고)
- `settings.ai_enabled` → 키가 비어 있지 않으면 True.
- 상수: `AI_MAX_FRAMES = 8`, `AI_OUTPUT_TOKENS = 600`, `AI_REQUEST_TIMEOUT_SECONDS = 60`, `AI_WORKERS = 2`, `SUMMARY_MAX_CHARS = 2000`.
- 키가 `sk-`로 시작하지 않으면 **경고만** 기록한다(프록시·호환 서버를 막지 않기 위해). 키 값은 기록하지 않는다.
- 시작할 때 기록 한 줄: `AI 요약: 사용 가능 (모델 …)` 또는 `AI 요약: 꺼짐 (OPENAI_API_KEY 없음)`.

### 5.3 "키만 넣으면 작동"을 위한 체크리스트
- [ ] `pip install -r requirements.txt` 한 번으로 `openai`와 ffmpeg가 모두 설치됨 (별도 프로그램 설치 없음)
- [ ] `alembic upgrade head` 한 번으로 DB 준비 (0004)
- [ ] `.env`에 `OPENAI_API_KEY=` 한 줄 추가 후 백엔드 재시작
- [ ] **연결 확인 명령** `python -m app.tools.check_ai` — 작은 테스트 이미지 한 장으로 키·모델·네트워크를 확인하고, 결과만 출력한다(키는 출력하지 않음). 문제가 있으면 무엇을 확인할지 알려준다. (기존 `DATABASE_URL` 점검 안내와 같은 방식)

## 6. OpenAI 호출 설계

### 6.1 어떤 API를 쓰는가
- OpenAI **Responses API**에 이미지를 `input_image`(base64 data URL)로 보낸다. 공식 가이드의 방식이다.
- 요청에는 **`store=False`**를 지정해 OpenAI 쪽에 응답이 저장되지 않게 한다.
- 영상은 파일을 직접 받지 않으므로 프레임(JPEG)을 여러 장 보낸다.
- 공식 `openai` 파이썬 패키지를 쓴다. **A2 첫 작업으로 설치된 버전(3.x)의 공식 문서를 읽고 호출 이름·매개변수를 확인한다.** 이 문서의 요청 모양은 설계 수준이며, 버전에 따라 이름이 다를 수 있다.

### 6.2 요청 구성

| 항목 | 값 |
| --- | --- |
| 모델 | `settings.openai_model` |
| 지시문(instructions) | 6.4의 고정 문장 |
| 사용자 입력 | 참고 정보 텍스트 1개 + 이미지 1장(이미지) 또는 프레임 최대 8장(영상) |
| `detail` | 모델 프로필에 따름 (6.3). 이미지는 `auto`, 영상 프레임은 타일 방식 모델이면 `low`, 패치 방식 모델이면 `auto` |
| 최대 출력 | 600토큰 (`max_output_tokens`) |
| 저장 여부 | `store=False` |
| 제한 시간 | 60초, SDK 재시도 2회 |

- **추론형(reasoning) 모델을 기본으로 정할 경우**: 출력 제한 600토큰이 내부 추론에 먼저 쓰여 요약이 비어 나올 수 있다. 추론 강도를 낮추는 설정이 있으면 적용하고, 그래도 비면 `empty` 실패로 처리하는 안전장치를 둔다. A2의 확인 항목에 넣는다.

### 6.3 모델 선택 정책

모델 이름은 코드에 고정하지 않고 `OPENAI_MODEL`로 바꿀 수 있다. 기본값은 `DEFAULT_OPENAI_MODEL` 상수 한 줄이다.

**공식 문서로 확인한 사실 (2026-10-27)**

| 항목 | `gpt-4o-mini` | `gpt-6-luna` |
| --- | --- | --- |
| 상태 | **2027-01-14에 API에서 제거 예정** (`gpt-4o-mini-2024-07-18`, 폐기 공지일 2026-10-14). 공식 권장 대체 모델이 `gpt-6-luna` | 위 폐기 공지의 공식 대체 모델 |
| 가격 (1M 토큰) | 입력 $0.15 / 출력 $0.60 | 입력 $0.10 / 출력 $0.50 |
| 이미지 입력 | 지원 | 지원 |

### 6.5 결과 처리와 오류 분류

**결과 처리**: 응답 텍스트를 앞뒤 공백 제거 → NUL 문자 제거 → 2,000자 초과 시 자르기 → 비어 있으면 `empty` 실패. 화면에는 **평문**으로만 표시한다(HTML로 해석하지 않음).

**오류 → 저장 코드 → 사용자 문구**

| 상황 | `analysis_error` | 사용자에게 보이는 문구 | 재시도 |
| --- | --- | --- | --- |
| 키가 없음 | (분석 안 함, `skipped`) | AI 요약을 사용할 수 없어요. | — |
| 결제·사용 한도 초과(429 중 `insufficient_quota`) | `billing` | AI 요약 서비스의 사용 한도를 확인해야 해요. 관리자 설정이 필요해요. | 설정 수정 후 |
| 키가 틀렸거나 권한 없음(401·403) | `auth` | AI 요약 서비스에 연결하지 못했어요. 관리자 설정을 확인해야 해요. | 설정 수정 후 |
| 사용 한도·요청 과다(429) | `rate_limit` | 지금은 요청이 많아요. 잠시 후 다시 시도해 주세요. | 가능 |
| 시간 초과·네트워크 | `timeout` | 요약하는 데 시간이 너무 오래 걸렸어요. 다시 시도해 주세요. | 가능 |
| 내용을 처리할 수 없다고 거부 | `refused` | 이 자료는 요약할 수 없어요. | 같은 결과 가능성 큼 |
| 모델이 없음·지원 안 함(404·400) | `model` | AI 요약 설정에 문제가 있어요. 관리자 설정을 확인해야 해요. | 설정 수정 후 |
| 서버 오류(5xx) | `server` | AI 서비스에 일시적인 문제가 있어요. 다시 시도해 주세요. | 가능 |
| 응답이 비어 있음 | `empty` | 요약을 만들지 못했어요. 다시 시도해 주세요. | 가능 |
| 영상 장면을 뽑지 못함 | `frames` | 영상에서 장면을 읽지 못했어요. | 같은 결과 가능성 큼 |
| 저장된 파일이 없음 | `file_missing` | 파일을 찾을 수 없어 요약하지 못했어요. | 불가 |
| 하루 한도 초과 | `quota` | 오늘 AI 요약 한도({n}회)를 다 썼어요. 내일 다시 시도해 주세요. | 내일 |
| 서버 재시작으로 중단 | `interrupted` | 서버가 다시 시작되어 요약이 중단됐어요. 다시 시도해 주세요. | 가능 |
| 그 밖 | `unknown` | 요약하지 못했어요. 잠시 후 다시 시도해 주세요. | 가능 |

- **OpenAI가 돌려준 오류 원문, 요청 내용, 키는 화면·응답·로그 어디에도 남기지 않는다.** 로그에는 자료 번호, 분류 코드, 모델 이름, 걸린 시간, 토큰 사용량만 남긴다.
- 사용자에게 `auth`·`model` 문구가 보이는 것은 개발자가 설정을 고쳐야 하는 문제임을 알리기 위함이다.

한도 차감(`reserve_quota`): 같은 문장에서 `UPDATE ai_usage SET count=count+1 WHERE user_id=? AND day=? AND count<한도`를 실행해 영향받은 행이 1이면 통과한다. 0이면 행이 없는 것인지(→ `INSERT count=1`, 중복 키 오류면 다시 UPDATE 1회) 한도에 닿은 것인지 구분한다. ## 7. 영상 프레임 추출 설계 (`app/video_frames.py`)

```python
def extract_frames(video_path: Path, max_frames: int = AI_MAX_FRAMES) -> list[bytes]  # JPEG 바이트, 시간순
```

1. ffmpeg 실행 파일: `imageio_ffmpeg.get_ffmpeg_exe()`. 가져오지 못하면 `frames` 실패.
2. **길이 확인**: `ffmpeg -i <파일>`을 실행해 오류 출력의 `Duration: HH:MM:SS.xx`를 읽는다. 읽지 못하면 길이를 모르는 것으로 보고 `fps=1`로 대체한다.
3. **프레임 추출**: 길이 D초일 때 `fps = max_frames / D`로 균등하게 뽑는다.
   ```
   ffmpeg -nostdin -hide_banner -loglevel error -protocol_whitelist file
          -i <파일> -an -sn -threads 1
          -vf "fps={fps},scale='min(768,iw)':-2" -frames:v {max_frames} -q:v 4
          <임시폴더>/f_%02d.jpg
   ```
4. 임시 폴더(`tempfile.TemporaryDirectory`)의 JPEG를 이름순으로 읽어 반환하고, **끝나면 반드시 지운다**.
5. 0장이면 `frames` 실패.

안전 장치:
- 사용자가 올린 파일을 서버 프로세스 안에서 해석하지 않고 **별도 프로세스**로 실행한다. 시간 제한 45초, 초과 시 프로세스를 종료한다. (`subprocess.run(..., timeout=…)`, 셸을 쓰지 않음)
- `-protocol_whitelist file`로 파일 외 입력(네트워크 등)을 막고, `-an -sn`으로 소리·자막은 처리하지 않는다.
- 이미 업로드 단계에서 앞부분 표식과 크기를 검사한 파일만 들어온다. (ffmpeg 자체의 취약점 위험은 완전히 없앨 수 없으므로 14장에 한계로 적는다.)

### 8.2 `app/analysis.py` — 분석 실행과 상태 관리
```python
def decide_initial_status(want_ai: bool) -> str            # 'pending' | 'skipped'
def submit(material_id: int) -> None                         # 실행기에 넣기 (테스트에서 즉시 실행으로 교체)
def run_analysis(material_id: int) -> None                   # 실행기 스레드에서 호출
def request_reanalysis(db, user, material_id) -> Material   # 다시 분석 API용: 조건부 UPDATE → pending → submit
def recover_interrupted() -> int                             # 시작 시: pending → failed(interrupted)
def reserve_quota(db, user_id) -> bool
```

`run_analysis` 단계 (**DB 연결은 OpenAI를 기다리는 동안 잡고 있지 않는다.** Supabase 연결 수 제한을 아끼고, 60초 동안 트랜잭션이 열려 있는 일을 막기 위해서다.):

1. 새 세션을 열어 자료를 읽는다. 없거나 `pending`이 아니면 종료한다. 읽은 값(종류, 제목, 메모, 저장 이름, 사용자 번호)을 변수로 옮기고 **세션을 닫는다**.
2. 파일 경로를 `storage.stored_path()`로 얻는다. 없으면 `file_missing`.
3. 이미지는 파일을 읽고, 영상은 `extract_frames`로 프레임을 얻는다. 영상 처리는 `frames` 오류로 변환한다.
4. 새 세션으로 `reserve_quota`. 한도 초과면 `quota`. 커밋하고 닫는다.
5. `openai_client.summarize(...)` 호출. (여기가 가장 오래 걸리는 구간)
6. 새 세션으로 **조건부 UPDATE** 한 번으로 결과를 저장한다.
   ```
   UPDATE materials SET summary=…, analysis_status='done', analyzed_at=now, analysis_model=…, analysis_error=NULL
   WHERE id=:id AND analysis_status='pending'
   ```
   영향받은 행이 0이면(그 사이 삭제됨) 결과를 버리고 기록만 남긴다.
7. 2~6의 어떤 단계에서든 예외가 나면 같은 조건부 UPDATE로 `failed`와 코드를 저장한다. 이 마지막 저장마저 실패하면 기록을 남기고, 다음 서버 시작 때 `recover_interrupted`가 정리한다.
8. 최상위에서 모든 예외를 잡는다. **분석 스레드의 오류가 서버나 다른 요청에 영향을 주지 않는다.**

실행기: 모듈 전역 `ThreadPoolExecutor(max_workers=2)`를 처음 쓸 때 만든다. `submit`은 `executor.submit(run_analysis, id)`이다.

### 8.3 시작 시 정리 (`app/main.py`의 lifespan)
- 서버가 시작될 때 `recover_interrupted()`를 한 번 실행한다. 이 서버 프로세스 안에서 분석이 돌고 있었다면 프로세스가 죽을 때 함께 사라지므로, **시작 시점의 `pending`은 모두 중단된 것**이다. → `failed(interrupted)`.
- 한계: 같은 데이터베이스를 쓰는 서버를 두 개 이상 동시에 켜면 이 가정이 깨진다. 현재 구성(서버 1개)에서는 안전하며, 14장에 한계로 적는다.
- 정리가 실패해도 서버 시작은 막지 않는다. (기록만 남김)

### 8.4 라우터 변경 (`app/routers/materials.py`)
- `create_material`: `ai_summary` 폼 값을 읽는다. (`"true"`/`"false"`, **없으면 켜짐으로 간주**: 기존 화면과 호환) `_create`가 상태를 정해 저장하고, commit 뒤 `analysis.submit(id)`를 부른다. `submit` 실패(실행기 오류)는 업로드를 실패시키지 않고 `failed(unknown)`으로 표시한다.
- `GET /api/materials`: 응답에 `ai_enabled`를 추가한다.
- `POST /api/materials/{id}/analyze`: 본인 자료만(`_own_material`, 없거나 남의 것이면 같은 404). `settings.ai_enabled`가 아니면 503. `request_reanalysis`로 조건부 전이, 실패하면 409.

### 10.3 폴링
- 목록에 `pending`이 하나라도 있는 동안 **3초마다** `GET /api/materials`를 조용히(`silent`) 다시 불러온다. 없어지면 즉시 멈춘다.
- 탭이 숨겨져 있으면(`document.hidden`) 건너뛴다. 화면을 떠나면 반드시 해제한다. (타이머 정리)
- 최대 5분. 그래도 `pending`이면 폴링을 멈추고 "요약이 오래 걸리고 있어요. 잠시 뒤 새로고침해 주세요."를 보여준다. (서버 쪽 자료는 그대로)
- 폴링 실패는 조용히 무시하고 다음 주기에 다시 시도한다. (목록을 오류 상태로 바꾸지 않음)
- 폴링으로 목록을 갈아 끼워도 등록 폼의 입력·선택 파일은 건드리지 않는다.

### 10.4 다시 분석
- 버튼을 누르면 `POST /analyze`. 응답이 오면 해당 카드를 `pending`으로 바꾸고 폴링이 이어받는다.
- 409(이미 분석 중·완료)이면 이유를 보여주고 목록을 새로 불러온다. 503이면 이유를 보여준다. 401은 기존처럼 로그인 화면으로 이동한다.
- 누르는 동안 해당 버튼은 비활성화한다.

### 10.5 접근성·표시
- 상태 변화(`분석 중` → `완료`)는 `aria-live="polite"`로 알린다.
- 요약문 안의 줄바꿈을 유지하고, 긴 단어는 `overflow-wrap: anywhere`로 줄바꿈한다.

## 12. 테스트 설계

### 12.1 서버 (자동, 실제 OpenAI 호출 없음)

**원칙**
- `tests/conftest.py`가 앱을 불러오기 **전에** `OPENAI_API_KEY`를 빈 값으로 설정한다. (환경 변수가 `.env`보다 우선하므로, 개발자의 실제 키가 `.env`에 있어도 테스트는 키가 없는 상태로 시작한다.)
- 모든 테스트에 자동으로 적용되는 장치가 `openai_client.create_client`를 **호출되면 즉시 실패하는 함수**로 바꾼다. AI를 시험하는 테스트만 가짜 클라이언트로 명시적으로 교체한다. → 실수로 실제 요청이 나가거나 돈이 드는 일이 없다.
- `analysis.submit`은 테스트에서 **즉시 실행(동기)** 으로 교체해 스레드 경쟁 없이 결과를 확인한다.

| ID | 시나리오 | 기대 |
| --- | --- | --- |
| B-01 | 키 없음 + 이미지 업로드 | 201, `skipped`, 파일·자료 저장됨, OpenAI 호출 없음 |
| B-02 | 키 있음 + 이미지 + `ai_summary` 없음/true | 201 `pending` → 실행 후 `done`, `summary` 저장, 모델 이름 저장 |
| B-03 | `ai_summary=false` | `skipped`, 호출 없음 |
| B-04 | 요청 모양 | 모델·`store=False`·출력 제한·`detail`·참고 정보(제목·메모)가 이미지보다 앞 |
| B-05 | 영상 업로드 | 프레임 여러 장이 시간순으로 한 요청에 전달됨 |
| B-06 | 오류 분류 전부 (`auth`, `rate_limit`, `timeout`, `refused`, `model`, `server`, `empty`) | `failed` + 코드 + 6.5 문구, 업로드 자체는 성공 상태 유지 |
| B-07 | 응답이 2,000자 초과 / 공백만 / NUL 포함 | 잘림 / `empty` / 제거 |
| B-08 | 하루 한도 | 한도까지 성공, 초과분 `failed(quota)`, 자료 삭제 후에도 횟수 유지, 날짜가 바뀌면 초기화(한국 날짜 경계) |
| B-09 | 한도 동시성 | 여러 스레드가 동시에 차감해도 한도를 넘지 않음 |
| B-10 | 파일이 사라진 자료 | `failed(file_missing)`, 한도 차감 없음 |
| B-11 | 프레임 추출 실패 | `failed(frames)`, 한도 차감 없음 |
| B-12 | 분석 중 자료 삭제 | 결과가 저장되지 않고 오류 없이 끝남, 한도는 차감됨 |
| B-13 | 서버 시작 정리 | `pending` → `failed(interrupted)`, 나머지 상태는 그대로 |
| B-14 | 다시 분석: `failed`/`skipped` | 202, `pending`으로 바뀌고 재실행 |
| B-15 | 다시 분석: `pending`/`done` | 409, 호출 없음 |
| B-16 | 다시 분석: 남의 자료·없는 자료 | 본문까지 같은 404 |
| B-17 | 다시 분석: 로그인 없음 / AI 꺼짐 | 401 / 503 |
| B-18 | 같은 자료를 동시에 두 번 다시 분석 | 한 번만 실행됨 (조건부 UPDATE) |
| B-19 | 비밀 노출 방지 | 정상·오류 모든 경우에 로그(`caplog`)와 응답 본문에 키 문자열이 없음. 설정 객체를 출력해도 키가 가려짐 |
| B-20 | AI 때문에 업로드가 실패하지 않음 | `submit`이 예외를 던져도 201과 자료가 남고 `failed(unknown)` |
| B-21 | 목록 응답 | `ai_enabled`, 항목별 분석 필드, `analysis_error`·`analysis_model`이 응답에 없음 |
| B-22 | 기존 학습 자료함 테스트 전체 | 변경 없이 통과 |
| B-23 | 마이그레이션 | 0003 → 0004 → 되돌리기, 기존 행이 `skipped`, 모델과 구조 일치 |
| B-24 | 프레임 추출 단위 | 프레임 수, 시간순, 폭 ≤ 768, 임시 폴더 정리, 시간 초과 시 프로세스 종료 |

### 12.2 화면 (자동)

| ID | 시나리오 | 기대 |
| --- | --- | --- |
| F-01 | `ai_enabled` + 체크박스 | 기본 켜짐, 전송 안내 문구 표시, 끄면 `ai_summary=false` 전송 |
| F-02 | `!ai_enabled` | 체크박스 없음, 설정 안내 표시 |
| F-03 | `pending` 카드 | "AI가 요약하는 중…" |
| F-04 | 폴링 | `pending`이 있으면 3초마다 목록 요청, `done`이 되면 요약 표시 후 폴링 중단 |
| F-05 | 폴링 수명 | 화면을 떠나면 타이머 해제, 탭이 숨겨지면 요청 안 함, 5분 뒤 안내 후 중단 |
| F-06 | 요약 표시 | 평문(HTML 태그가 문자 그대로 보임), 길면 "더 보기/접기" |
| F-07 | `failed` | 문구와 "다시 분석" → `POST /analyze` → `pending` 전환 |
| F-08 | 다시 분석 409/503/401 | 이유 표시·목록 새로고침·로그인 이동 |
| F-09 | `skipped` + `ai_enabled` | "AI 요약 만들기" 버튼, `!ai_enabled`이면 표시 없음 |
| F-10 | 하단 AI 영역 | 사용 중/설정 필요 문구, 비활성 "연결 예정" 버튼 없음 |
| F-11 | 폴링 중 입력 유지 | 등록 폼에 입력 중이어도 목록 갱신이 입력·선택 파일을 지우지 않음 |
| F-12 | 기존 학습 자료함 테스트 | 새 응답 필드를 모르는 기존 목업에서도 통과 (필드 없음 = 안전한 기본값) |

### 12.3 수동·통합 (A7)
- 실제 키로 이미지·영상 각 1건, 요약 품질(주제·핵심·읽을 수 없는 경우 처리), 응답 시간, OpenAI 콘솔의 사용량·비용, 요약에 비밀값이 옮겨 적히지 않는지 눈으로 확인.
- 자동 테스트는 SQLite이므로 PostgreSQL 동작(`ai_usage` 차감, 조건부 UPDATE, 새 CHECK)은 A7에서 Supabase로 직접 확인한다.

**실측 (A7, `gpt-6-luna`, 임시 서버)**

| 항목 | 결과 |
| --- | --- |
| 업로드 응답 시간 | 약 0.02초 (분석을 기다리지 않음) |
| 이미지(636×174) | 입력 451~455 / 출력 49~52 토큰, 2~4초 |
| 영상(6초, 장면 8장, 640×360) | 입력 2,628 / 출력 113 토큰, 약 2~3초 |
| 4회 호출 합계 | 약 $0.0005 (이미지 1회 약 $0.0001, 영상 1회 약 $0.0003) |

- 3장의 비용 계산(6.3)의 `gpt-6-luna` 열과 맞는다. 큰 사진(수 MB)의 토큰 수는 아직 실측하지 않았다. 실제 사용량은 서버 기록의 `input_tokens`, OpenAI 콘솔에서 확인할 수 있다.
- 자동 테스트: 서버 366개, 화면 92개. 실제 키 확인: 임시 서버 29항목, Supabase(롤백) 14항목.
- 확인하지 못한 것: 브라우저에서 눈으로 본 화면(레이아웃, 접기/펼치기, 작은 화면), 큰 사진·긴 영상의 실제 비용, PostgreSQL에서의 동시 요청(동시 차감은 SQLite 테스트로 확인했고, PostgreSQL은 같은 단일 `UPDATE … WHERE count < 한도`라 행 잠금으로 안전하다고 보지만 직접 시험하지는 않음).
