# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버(FastAPI)에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, `node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- FastAPI와 React의 기본 기능을 우선 사용하고, 꼭 필요하지 않은 외부 패키지는 추가하지 않습니다.
- 개발과 자동 테스트는 SQLite로 진행하고, 같은 코드가 Supabase(PostgreSQL)에서도 동작하도록 한쪽 데이터베이스에서만 되는 기능은 사용하지 않습니다.

## 3. 기술 구성

| 구분 | 사용할 기술 | 역할 |
| --- | --- | --- |
| 화면 | React, Vite, React Router | 사용자가 보는 화면과 화면 이동 |
| 화면 테스트 | Vitest, React Testing Library | 화면 동작 자동 테스트 |
| 서버 | Python, FastAPI | 화면의 요청을 받아 검사·저장·조회 |
| 입력값 검사 | Pydantic | 글자 수, 형식 같은 입력 조건 검사 |
| 데이터베이스 연결 | SQLAlchemy | SQLite와 Supabase를 같은 코드로 사용 |
| 데이터베이스 구조 변경 기록 | Alembic | 표(테이블)를 만들고 바꾼 이력을 순서대로 관리 |
| 서버 테스트 | pytest | 서버 기능 자동 테스트 |
| 데이터베이스 | SQLite (개발·테스트), Supabase (실제 서비스) | 데이터 저장 |

### 3.1 서로 어떻게 연결되나요?

```text
브라우저 (React 화면)
   │  /api 로 시작하는 요청
   ▼
FastAPI 서버  ──  로그인 확인, 권한 검사, 입력값 검사
   │
   ▼
데이터베이스  ──  개발·테스트: SQLite 파일 / 실제 서비스: Supabase
```

- React 화면은 데이터베이스에 직접 접속하지 않고, 항상 FastAPI 서버를 거칩니다.
- 회원가입·로그인은 FastAPI가 직접 처리합니다. Supabase의 로그인 기능(Supabase Auth)은 사용하지 않습니다. SQLite로 테스트할 때와 Supabase를 쓸 때 로그인 방식이 같아야 하기 때문입니다.
- Supabase는 데이터베이스(PostgreSQL)로만 사용합니다.
- 로그인 상태는 브라우저가 JavaScript로 읽을 수 없는 쿠키(httpOnly 쿠키)로 유지합니다.
  - 로그인하면 서버가 추측할 수 없는 임의의 값(로그인 표)을 만들어 쿠키에 담고, 데이터베이스에는 그 값을 변환한 값만 저장합니다.
  - 로그아웃하면 데이터베이스의 로그인 표를 지워서, 쿠키가 남아 있어도 더 이상 쓸 수 없게 합니다.
  - 로그인은 마지막 로그인부터 7일 동안 유지합니다.
- 개발 중에는 React 개발 서버가 `/api` 요청을 FastAPI 서버로 전달(프록시)해서, 화면과 서버를 같은 주소처럼 사용합니다.

### 3.2 개발 서버 주소

| 구분 | 주소 |
| --- | --- |
| React 개발 서버 | `http://127.0.0.1:5173` |
| FastAPI 개발 서버 | `http://127.0.0.1:8000` |

### 3.3 환경 변수

비밀값은 `backend/.env`에 두고, 항목 이름만 `backend/.env.example`에 기록합니다.

| 이름 | 설명 | 예시 (비밀값 아님) |
| --- | --- | --- |
| `APP_ENV` | 실행 환경 | `development`, `test`, `production` |
| `DATABASE_URL` | 데이터베이스 주소 | `sqlite:///../database/buildlog.sqlite3` |

- 로그인 표를 데이터베이스에 저장하는 방식이라 쿠키 서명용 비밀값은 따로 두지 않습니다.

- Supabase 연결 주소에는 비밀번호가 들어 있으므로 `.env`에만 저장합니다.
- 화면(React) 쪽에는 비밀값을 두지 않습니다.

## 4. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ .env.example
│  ├─ alembic.ini
│  ├─ alembic/             # 데이터베이스 구조 변경 기록
│  ├─ app/
│  │  ├─ main.py           # FastAPI 시작점
│  │  ├─ config.py         # 환경 변수 읽기
│  │  ├─ database.py       # 데이터베이스 연결

│  │  ├─ models/           # 데이터베이스 표 정의
│  │  ├─ schemas/          # 입력·출력 형식과 입력값 검사
│  │  ├─ routers/          # 기능별 요청 처리
│  │  │  ├─ auth.py        # 회원가입, 로그인, 로그아웃
│  │  │  ├─ account.py     # 닉네임 변경
│  │  │  ├─ studies.py     # 공부 기록
│  │  │  ├─ todos.py       # 할 일
│  │  │  ├─ errors.py      # 오류 기록
│  │  │  ├─ public.py      # 공개 기록
│  │  │  ├─ comments.py    # 댓글
│  │  │  ├─ likes.py       # 좋아요
│  │  │  └─ reports.py     # 신고, 운영자 확인
│  │  └─ permissions.py    # 작성자·운영자 권한 검사
│  └─ tests/
├─ frontend/
│  ├─ package.json
│  ├─ vite.config.js
│  ├─ index.html
│  └─ src/
│     ├─ main.jsx
│     ├─ App.jsx           # 화면 이동(라우팅)
│     ├─ api/              # 서버 요청 함수
│     ├─ pages/            # 화면 단위
│     ├─ components/       # 버튼, 카드, 입력칸 같은 공통 조각
│     └─ styles/           # CSS
├─ database/
│  └─ buildlog.sqlite3     # 개발용 데이터 파일, Git 제외
└─ docs/                   # 요구사항, 동작 설명서, 개발 문서
```

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 이 컴퓨터에 설치된 Python, Node.js, npm의 버전을 확인합니다.
4. 그 버전과 서로 호환되는 FastAPI, SQLAlchemy, Alembic, Pydantic, React, Vite의 안정 버전을 정합니다.
5. 비밀번호를 안전하게 저장할 방식(검증된 비밀번호 해시 라이브러리)을 정합니다.
6. 화면 코드를 JavaScript로 쓸지 TypeScript로 쓸지 정합니다.
7. 개발 서버 주소, 데이터베이스 파일 위치, 환경 변수 이름을 확정합니다.
8. 테스트 명령과 서버 실행 명령을 문서에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python, Node.js, npm 실행 여부와 버전을 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

#### 목표

기능 없이도 FastAPI 서버와 React 화면이 실행되고, 화면이 서버의 응답을 받아 표시하게 합니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 준비합니다.
2. FastAPI, 실행 서버(uvicorn, 자동 재시작용 watchfiles), 설정 읽기(pydantic-settings), 서버 테스트(pytest, httpx2) 패키지만 먼저 설치하고 정확한 버전을 `backend/requirements.txt`에 기록합니다. `uvicorn[standard]`는 쓰지 않습니다. (8장 참고)
3. `backend/app/main.py`에 서버 상태를 알려주는 확인용 주소(`/api/health`) 하나만 만듭니다.
4. 환경 변수를 `backend/app/config.py`에서 읽도록 하고 `backend/.env.example`에는 항목 이름만 기록합니다.
5. `frontend`에 Vite로 React 프로젝트를 만듭니다.
6. React 개발 서버가 `/api` 요청을 FastAPI 서버로 전달하도록 설정합니다.
7. React 첫 화면에서 `/api/health` 응답을 받아 "서버 연결됨"을 표시합니다.
8. SQLite 파일, 테스트·빌드 중 생성되는 파일을 `.gitignore`에 보완합니다.
9. 이 Phase에서는 아직 데이터베이스를 만들지 않습니다. 사용자 모델을 먼저 만들어야 하기 때문입니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/.env.example`
- `backend/pytest.ini`
- `backend/app/main.py`
- `backend/app/config.py`
- `backend/tests/test_health.py`
- `frontend/package.json`
- `frontend/package-lock.json`
- `frontend/vite.config.js`
- `frontend/index.html`
- `frontend/src/main.jsx`
- `frontend/src/App.jsx`
- `frontend/src/App.test.jsx`
- `frontend/src/api/health.js`
- `frontend/src/test/setup.js`
- `frontend/src/styles/base.css`
- `.gitignore`

#### 확인 방법

- FastAPI 서버가 오류 없이 시작되고 `/api/health`가 응답하는지 확인합니다.
- React 개발 서버가 오류 없이 시작되고 브라우저에 첫 화면이 보이는지 확인합니다.
- 첫 화면에 서버 응답이 표시되는지 확인합니다.
- 비밀 설정값과 SQLite 파일, `node_modules`가 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 두 서버와 첫 화면이 정상 실행되어야 합니다.
- 사용자 모델을 만들기 전에는 데이터베이스 구조를 만들지 않습니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. SQLAlchemy와 Alembic을 설치하고 `requirements.txt`에 기록합니다.
2. `backend/app/database.py`에서 `DATABASE_URL`로 데이터베이스에 연결합니다.
3. 사용자 모델을 만듭니다.
4. 이메일은 필수이며 중복되지 않게 합니다. 대소문자만 다른 이메일도 같은 이메일로 봅니다.
5. 닉네임은 필수이며 중복되지 않게 합니다.
6. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용합니다.
7. 비밀번호는 원문 대신 Phase 0에서 정한 방식으로 안전하게 처리한 값만 저장합니다.
8. 운영자인지 구분하는 값을 사용자 모델에 둡니다. 기본값은 일반 사용자이며, 화면에서 바꿀 수 없습니다.
9. Alembic으로 첫 구조 기록을 만들고 빈 SQLite 데이터베이스에 적용합니다.
10. 자동 테스트는 개발용 데이터 파일과 분리된 테스트용 SQLite 데이터베이스를 사용합니다.
11. 사용자 모델 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/app/database.py`
- `backend/app/models/user.py`
- `backend/app/security.py`
- `backend/alembic.ini`
- `backend/alembic/`
- `backend/tests/conftest.py`
- `backend/tests/test_user_model.py`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.

### Phase 4. 공부 기록·할 일·오류 기록의 데이터 구조

#### 작업

1. 공부 기록 모델을 만듭니다.

   - 작성자, 오류 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부

9. Alembic 구조 기록을 만들고 적용합니다.

### Phase 13. Supabase 연결

#### 목표

SQLite로 완성한 기능이 실제 서비스용 데이터베이스인 Supabase에서도 똑같이 동작하게 합니다.

#### 작업

1. PostgreSQL 연결에 필요한 패키지를 설치하고 `requirements.txt`에 기록합니다.
2. 사용자가 만든 Supabase 프로젝트의 연결 주소를 `backend/.env`의 `DATABASE_URL`에 넣습니다. 연결 주소는 사용자가 직접 넣고, 문서나 코드에는 기록하지 않습니다.
3. 지금까지 만든 Alembic 구조 기록을 Supabase에 순서대로 적용합니다.
4. Supabase의 모든 BuildLog 표에 RLS(행 단위 보안)를 켜고 허용 규칙은 만들지 않습니다. FastAPI 서버만 데이터에 접근하고, Supabase의 공개 주소로는 데이터를 읽거나 쓸 수 없게 하기 위해서입니다.
5. 서버 자동 테스트를 Supabase와 같은 종류의 데이터베이스에서 한 번 실행합니다. 이때 실제 데이터와 섞이지 않도록 테스트 전용 데이터베이스나 테스트 전용 Supabase 프로젝트를 사용합니다.
6. 날짜·시간, 검색의 대소문자 처리, 중복 방지 제약이 SQLite와 같은 결과를 내는지 확인합니다.
7. 개발용 SQLite로 다시 돌아갈 때는 `DATABASE_URL`만 바꾸면 되도록 유지합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/.env.example`
- `backend/alembic/versions/` (필요한 경우 RLS 설정)
- `backend/tests/conftest.py`
- `docs/setup.md`

#### 확인 방법

- Supabase에 BuildLog의 모든 표가 만들어졌는지 확인합니다.
- Supabase에 연결한 상태에서 회원가입·로그인·기록·공개·댓글·좋아요·신고 흐름이 동작하는지 확인합니다.
- Supabase의 공개 주소로 BuildLog 표를 읽을 수 없는지 확인합니다.
- `DATABASE_URL`을 SQLite로 바꾸면 그대로 다시 동작하는지 확인합니다.
- 연결 주소와 비밀번호가 Git 기록 대상이나 문서에 들어 있지 않은지 확인합니다.

#### 완료 조건

- 같은 코드와 자동 테스트가 SQLite와 Supabase 양쪽에서 통과해야 합니다.
- 비밀값이 노출된 곳이 없어야 합니다.

| 크기 검사 | 파일을 조금씩 읽으며 한도를 넘는 순간 중단 (Content-Length 값을 믿지 않음) | 거짓 크기 표시나 매우 큰 파일로 서버가 메모리·디스크를 소모하는 것을 막음 |
| MB 계산 | 1MB = 1,048,576바이트 (5MB = 5,242,880, 30MB = 31,457,280) | 문서·서버·화면이 같은 값을 써야 경계 테스트가 일치함 |
| 원본 보기 방식 | `GET /api/materials/{id}/file`이 로그인과 소유자를 확인한 뒤 파일을 직접 전달 | 업로드 폴더를 정적 주소로 공개하면 주소를 아는 누구나 볼 수 있어 비공개가 깨짐 |
| 다른 사람의 자료 | 존재하지 않는 자료와 똑같이 404 "자료를 찾을 수 없습니다." | 403으로 답하면 그 번호의 자료가 있다는 사실이 새어 나감 |
| 브라우저에 알리는 형식 | 저장된 형식(`image/png`, `image/jpeg`, `video/mp4`)만 전달하고 `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store`를 붙임 | 업로드된 파일이 다른 형식으로 해석되거나 공유 캐시에 남는 것을 막음 |
| 영상 탐색 | 부분 전송(Range) 요청을 지원 | 영상의 재생 위치 이동에 필요. 설치된 Starlette의 `FileResponse`가 지원하는지 M4에서 직접 확인 |
| 저장 순서 (등록) | 파일을 임시 이름으로 쓰며 검사 → 자료 정보를 데이터베이스에 넣되 확정하지 않기(flush) → 파일을 최종 이름으로 바꾸기 → 자료 정보 확정(commit). 중간에 실패하면 임시·최종 파일을 지우고 데이터베이스 변경도 되돌림 (M3에서 "확정"과 "이름 바꾸기" 순서를 바꿈) | "정보만 있고 파일 없음"이 사용자 화면에 보이는 것을 막음. 프로그램이 도중에 멈추더라도 남는 것은 어디서도 접근할 수 없는 파일뿐임 |
| 저장 순서 (삭제) | 자료 정보를 먼저 지우고 확정한 뒤 파일을 지움. 파일을 못 지우면 기록만 남김 | 반대로 하면 파일이 없는 자료 정보가 남아 사용자 화면에 깨진 자료가 보임. 남는 파일은 어디서도 접근할 수 없음 |
| 자료와 사용자 연결 | `user_id` 외래 키, 사용자 삭제 시 함께 삭제(`ON DELETE CASCADE`) | `login_sessions`와 같은 방식 |
| 새 환경 변수 | 없음. 업로드 폴더와 크기 한도는 코드의 상수 | 비밀값이 아니고 `.env` 설정이 늘어나지 않음 |

### 9.3 만들거나 바꿀 파일

**데이터베이스 표 `materials`**

| 열 | 형식 | 조건 | 설명 |
| --- | --- | --- | --- |
| `id` | Integer | 기본 키 | 자료 번호 |
| `user_id` | Integer | 필수, `users.id` 외래 키(CASCADE), 인덱스 | 자료를 올린 사람 |
| `title` | String(100) | 필수 | 공백 제거한 제목 |
| `memo` | String(1000) | 비어 있을 수 있음 | 메모. 입력하지 않으면 비움(NULL) |
| `kind` | String(10) | 필수, `image` 또는 `video` | 필터용 종류 |
| `original_filename` | String(255) | 필수 | 표시용 원래 파일 이름 |
| `content_type` | String(20) | 필수 | `image/png`, `image/jpeg`, `video/mp4` 중 하나 |
| `size_bytes` | Integer | 필수 | 파일 크기 |
| `storage_name` | String(64) | 필수, 유일 | 서버에 저장된 파일 이름 |
| `created_at` | DateTime(timezone) | 필수 | UTC로 저장 |

- 목록 조회용 인덱스: `(user_id, created_at, id)`. 종류가 두 가지뿐이므로 `kind` 인덱스는 만들지 않습니다.
- 값 범위(`kind`, `content_type`)와 `size_bytes > 0`은 서버가 검사하고, 데이터베이스에도 CHECK 조건을 둡니다. (M2에서 결정: `ck_materials_kind`, `ck_materials_content_type`, `ck_materials_size_positive`. 단순한 SQL이라 SQLite·PostgreSQL에서 같게 동작하며, SQLite 테스트로 확인했습니다.)
- 마이그레이션 `0003_create_materials.py`의 `downgrade`는 표만 지우며 `backend/uploads`의 파일은 지우지 않습니다. 파일 정리는 사람이 직접 합니다.

**서버 주소**

| 방식·주소 | 하는 일 | 성공 | 실패 |
| --- | --- | --- | --- |
| `POST /api/materials` (multipart: `title`, `memo`, `file`) | 자료 등록 | 201 + 자료 정보 | 401 로그인 필요, 413 크기 초과(`field: file`), 415 허용하지 않는 형식(`field: file`), 422 제목·메모·파일 누락(`field` 지정) |

- 자료 정보 응답에는 서버 내부 정보(`storage_name`, 서버 경로, `user_id`)를 넣지 않습니다. 화면에는 번호, 제목, 메모, 종류, 원래 이름, 형식, 크기, 등록 시각만 보냅니다.

각 단계가 끝나면 결과를 보고하고, 사용자가 승인한 뒤에 다음 단계를 시작합니다. (`CLAUDE.md` 규칙 2) 단계마다 `docs/progress.md`에 완료한 것과 확인하지 못한 것을 기록합니다.

#### M1. 파일 선택 (화면만)

**목표**: 파일을 고르고, 서버에 보내기 전에 화면에서 조건을 검사해 보여줍니다. 서버로는 아무것도 보내지 않습니다.

1. "파일 선택" 버튼을 켜고, 숨겨진 파일 입력(`accept="image/png,image/jpeg,video/mp4"`)을 연결합니다.
2. 고른 파일을 검사합니다: 확장자·형식(PNG, JPG, MP4), 비어 있는지, 크기(PNG·JPG 5MB, MP4 30MB). 기준값은 `frontend/src/materialFile.js`에 한 번만 적습니다.
3. 통과하면 파일 이름·형식·크기를 파일 영역에 보여주고 "다른 파일 선택" 또는 "선택 취소"를 제공합니다. 실패하면 이유를 파일 영역 아래에 보여주고 선택은 비웁니다.
4. 제목·메모의 길이 안내(100자, 1,000자)를 입력칸 아래에 보여줍니다. 제한은 화면에서 막지 않고 검사 결과로 알립니다.
5. "자료 업로드"는 **계속 비활성화**하고 "업로드는 다음 단계에서 연결됩니다" 안내를 유지합니다. 성공을 가장하지 않습니다.
6. 화면 테스트: 허용 형식, 경계 크기(정확히 5MB와 5MB+1바이트, 30MB와 30MB+1바이트), 거절 형식, 빈 파일, 선택 취소를 확인합니다.

**변경**: `MaterialsPage.jsx`, `materials.css`, `materialFile.js`, `App.test.jsx`. 서버·데이터베이스는 변경 없음.
**완료 기준**: 화면 테스트와 빌드 통과. 브라우저에서 파일을 골라 보고 거절 메시지를 직접 확인.

#### M2. 테이블 준비

**목표**: Supabase에 `materials` 표를 만들 수 있는 상태로 준비합니다.

1. `app/models/material.py`에 `Material` 모델을 만들고 `models/__init__.py`에 등록합니다. (9.3의 열 정의)
2. Alembic 마이그레이션 `0003_create_materials.py`를 만듭니다. 표, 외래 키(CASCADE), `storage_name` 유일 제약, 목록용 인덱스를 포함하고 `downgrade`를 함께 만듭니다.
3. `config.py`에 상수를 추가합니다: 업로드 폴더(`backend/uploads/materials`), PNG·JPG 한도, MP4 한도. 폴더는 처음 파일을 저장할 때 만듭니다. 서버 시작 시 만들지 않습니다.
4. 테스트(SQLite): 마이그레이션이 빈 데이터베이스에 적용되는지, 모델과 마이그레이션의 열이 일치하는지, 사용자를 지우면 자료 정보도 지워지는지, `storage_name` 중복이 거절되는지. 기존 `test_migrations.py`의 방식을 따릅니다.
5. 테스트가 실제 `backend/uploads`를 건드리지 않도록 테스트용 폴더를 쓰는 준비를 `tests/conftest.py`에 합니다.
6. 사용자가 실행할 명령(`backend` 폴더): `.\.venv\Scripts\alembic upgrade head`. 같은 명령을 다시 실행해도 `0003`이 다시 적용되지 않습니다. 실제 Supabase에는 **사용자가 이 명령을 실행하고 알려준 뒤에** 만들어졌다고 보고합니다.

**변경**: `models/material.py`, `models/__init__.py`, `config.py`, `alembic/versions/0003_*.py`, 테스트. 기존 표와 기능은 변경 없음.
**완료 기준**: 서버 전체 테스트 통과. Supabase 반영은 사용자가 명령 실행 후 Table Editor에서 `materials` 표를 확인.

#### M3. 업로드 API

**목표**: `POST /api/materials`가 안전하게 파일과 자료 정보를 저장합니다.

1. 패키지 설치: `python-multipart` (정확한 버전을 확인해 `requirements.txt`에 고정). 설치한 사실을 보고합니다.
2. `app/storage.py`:
   - 파일을 청크 단위로 임시 이름에 쓰면서 크기를 세고, 한도를 넘으면 즉시 중단하고 임시 파일을 지웁니다. 종류별 한도는 앞부분 표식으로 종류를 알아낸 뒤 적용합니다.
   - 앞부분 표식으로 PNG·JPG·MP4를 판별하고, 확장자·형식 이름과 서로 일치하지 않으면 거절합니다.
   - 최종 파일 이름(`uuid4` + 확장자)을 만들고, 임시 파일을 최종 이름으로 바꿉니다. 저장 경로는 항상 업로드 폴더 안인지 확인합니다.
   - 원래 파일 이름의 경로 구분자와 제어 문자를 제거하고 255자로 자릅니다.
3. `schemas/material.py`: 제목(공백 제거 후 1~100자), 메모(공백 제거 후 최대 1,000자, 비면 비움) 검사. 제목·메모 오류는 `field`를 지정한 422로 반환합니다.
4. `routers/materials.py`: 로그인 확인 → 제목·메모 검사 → 파일 저장(검사 포함) → 데이터베이스에 정보 저장 → 최종 이름으로 확정. **어느 단계에서든 실패하면 임시·최종 파일과 데이터베이스 변경을 모두 되돌리고** 사용자에게 한국어 이유를 돌려줍니다. 응답에 서버 경로를 넣지 않습니다.
5. 오류 매핑: 크기 초과 413(`field: file`), 허용하지 않는 형식·가짜 파일·빈 파일 415 또는 422(`field: file`), 파일 없음 422(`field: file`), 파일이 2개 이상이면 거절.
6. `main.py`에 주소를 등록합니다.
7. 테스트(임시 업로드 폴더, 임시 SQLite):
   - 정상: PNG, JPG, MP4 각각 201, 파일이 저장되고 정보가 맞음.
   - 경계: 정확히 5MB PNG·JPG와 30MB MP4 통과, 각각 1바이트 초과는 거절.
   - 거절: 제목 공백만·101자, 메모 1,001자, 파일 없음, 빈 파일, GIF/SVG/WebP, 확장자만 `.png`로 바꾼 텍스트·MP4, 형식 이름과 내용이 다른 파일, 파일 2개.
   - 정리: 거절·데이터베이스 저장 실패(강제로 오류를 내서)·파일 쓰기 실패 뒤에 `uploads`에 파일이 남지 않고 `materials`에 행이 늘지 않음.
   - 보안: 파일 이름이 `../../x.png`여도 폴더 밖에 쓰지 않고, 사용자가 정한 이름이 저장 이름에 쓰이지 않음. 응답에 `storage_name`·경로 없음.
   - 권한: 로그인하지 않으면 401이며 파일이 저장되지 않음. 자료는 항상 로그인한 사용자 소유.
   - 기존 서버 테스트(65개)가 계속 통과.

**변경**: `requirements.txt`, `storage.py`, `schemas/material.py`, `routers/materials.py`, `main.py`, 테스트.
**완료 기준**: 서버 전체 테스트 통과. 임시 폴더 테스트 외에, 사용자가 서버를 켠 상태에서 실제 요청(API 문서 화면 또는 `curl`)으로 올려 보고 Supabase `materials` 표에 행이 생긴 것을 확인.

#### M4. 조회·삭제 API

**목표**: 목록, 원본 전달, 삭제를 만들고 소유자 검사를 완성합니다.

1. `GET /api/materials`: 로그인한 사용자의 자료만 `created_at` 내림차순(같은 시각이면 `id` 내림차순)으로 반환하고, 필터와 관계없는 종류별 개수(`counts`)를 함께 보냅니다. `kind`가 `image`·`video`가 아니면 422.
2. `GET /api/materials/{id}/file`: 본인 자료만 조회(`id`와 `user_id`를 함께 조건으로). 없거나 남의 것이면 404. 데이터베이스에는 있는데 파일이 없으면 404와 서버 기록(경로는 서버 기록에만). 저장된 `content_type`, `nosniff`, `Cache-Control: private, no-store`, 파일 이름이 없는 `inline`을 붙이고 Range 요청을 지원합니다.
3. `DELETE /api/materials/{id}`: 본인 자료만. 정보를 지우고 확정한 뒤 파일을 지웁니다. 파일이 없어도 성공으로 처리하고, 지우지 못하면 서버 기록에 남깁니다.
4. 테스트:
   - 목록: 본인 것만, 최신순, 같은 시각 순서, 필터, `counts`, 빈 목록.
   - 격리: 두 사용자를 만들어 A의 자료 번호로 B가 목록·원본·삭제를 시도 → 모두 404이고 A의 자료와 파일이 그대로. 없는 번호의 응답과 **본문까지 같음**.
   - 원본: 형식 헤더, `nosniff`, Range 응답(영상 일부 요청이 206), 로그인하지 않으면 401.
   - 삭제: 행과 파일이 함께 사라짐. 이미 지운 자료를 다시 지우면 404. 파일이 이미 없어도 삭제 성공. 삭제 후 원본 주소가 404.
   - 로그아웃 후 세 주소 모두 401.
5. 데이터베이스 확인: SQLite 테스트 통과 후, 실제 Supabase에서 같은 흐름(등록 → 목록 → 원본 → 삭제)을 사용자가 직접 확인합니다.

**변경**: `routers/materials.py`, `schemas/material.py`, 테스트.
**완료 기준**: 서버 전체 테스트 통과. Supabase에서 시간 순서와 격리가 SQLite와 같은 결과인지 확인.

#### M5. 화면 연결

**목표**: `/materials` 화면의 예시 목록을 실제 서버 데이터로 바꾸고 모든 기능을 연결합니다.

1. `api/materials.js`: 목록, 등록(`FormData`), 삭제 요청. 등록은 `Content-Type` 헤더를 직접 지정하지 않습니다(브라우저가 경계값을 넣음). 서버 오류는 기존 `ApiError`로 변환하고, 네트워크 오류는 기존 방식의 문구를 사용합니다.
2. 목록: 화면 진입 시 불러오기(불러오는 중·실패와 다시 시도·빈 목록 상태). 필터 숫자는 서버의 `counts`를 사용합니다. 로그인 만료(401)는 로그인 화면으로 보냅니다.
3. 등록: 서버 검사 오류를 `field`에 맞는 입력칸 아래에 표시합니다. 업로드 중에는 버튼을 비활성화해 중복 전송을 막습니다. 성공하면 입력칸과 파일 선택을 비우고 목록을 다시 불러옵니다. **실패하면 입력값과 선택한 파일을 유지**합니다.
4. 원본 보기: `/api/materials/{id}/file`을 새 탭으로 엽니다(`target="_blank"`, `rel="noopener"`). 목록의 이미지 미리보기는 같은 주소를 `loading="lazy"`로 사용하고, 영상은 ▶ 표시를 유지합니다.
5. 삭제: 확인창에서 동의한 경우에만 요청하고, 성공하면 목록과 숫자를 갱신합니다. 실패 시 이유를 알리고 자료를 남깁니다. 이미 지워진 경우 목록을 새로 불러옵니다.
6. 예시 데이터를 제거하고 "디자인 확인용 예시" 표시와 "화면만 준비되어 있어요" 안내를 실제 상태 안내로 바꿉니다. 사이드바 "나만의 학습 공간" 안내와 AI 영역(연결 예정, 비활성화)은 유지합니다. AI를 호출하지 않습니다.
7. 화면 테스트(가짜 서버): 목록 표시·빈 상태·실패 상태, 등록 성공(입력 비움·목록 갱신)과 실패(입력 유지), 서버 검사 오류의 입력칸 표시, 업로드 중 중복 클릭 방지, 삭제 확인·취소·실패, 401 이동.
8. 작은 화면(720px, 360px)에서 등록 폼과 목록이 세로로 쌓이고 가로 스크롤이 없는지 확인합니다.
9. 전체 확인: 두 계정으로 격리를 확인하고, 서버를 껐다 켠 뒤에도 자료가 남는지 확인합니다.

**변경**: `api/materials.js`, `MaterialsPage.jsx`, `materials.css`, `App.test.jsx`. 서버는 변경 없음.
**완료 기준**: 화면 테스트·서버 테스트·빌드 통과, 사용자가 브라우저에서 등록 → 목록 → 원본 → 삭제를 직접 확인.

### 9.6 위험과 아직 정하지 않은 것

**알고 시작할 한계**

- 파일은 서버의 `backend/uploads` 디스크에, 자료 정보는 Supabase에 따로 저장됩니다. 두 곳이 한 번에 저장되는 것이 아니므로 9.2의 저장 순서로 어긋남을 최소화하지만, **서버 디스크가 사라지거나 다른 컴퓨터로 옮기면 파일이 없어져 자료 정보만 남습니다.** 이 경우 원본 보기는 "자료를 찾을 수 없습니다."로 답합니다. Supabase 데이터베이스를 백업해도 이 파일은 포함되지 않습니다.
- 서버를 인터넷에 배포할 때 업로드 폴더가 재배포마다 지워지는 환경이면 자료가 사라집니다. 배포 방식이 정해질 때 파일 저장소를 다시 논의해야 합니다.
- 삭제에서 정보만 지워지고 파일이 남는 경우가 생길 수 있어, 서버 기록에 남겨 사람이 정리합니다. 자동 정리 기능은 이번에 만들지 않습니다.
- 사용자별 총 용량 제한이 없어 한 사용자가 서버 디스크를 채울 수 있습니다.
- 이미지 미리보기는 원본 파일을 그대로 쓰므로(축소본 없음) 5MB 이미지가 여러 장이면 목록이 느릴 수 있습니다.
- 이미지·영상 내용 자체를 검사하지는 않습니다. 앞부분 표식과 형식만 확인합니다.
