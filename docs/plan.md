# BuildLog MVP 개발 계획

## 1. 계획의 목적

이 문서는 `spec.md`에 정한 기능을 어떤 순서로 개발할지 설명합니다.

처음 개발하는 과정에서 한 번에 너무 많은 내용을 다루지 않도록 작업을 작은 Phase로 나눕니다. 한 번의 작업에서는 Phase 하나만 진행하고, 확인 기준을 모두 통과한 뒤 다음 Phase로 넘어갑니다.

## 2. 개발 원칙

- `spec.md`에 없는 기능은 추가하지 않습니다.
- 각 Phase가 끝날 때 자동 테스트와 직접 화면 확인을 함께 수행합니다.
- 확인에 실패하면 다음 Phase로 넘어가지 않고 현재 Phase만 수정합니다.
- 화면에서 버튼을 숨기는 것만으로 권한을 처리하지 않습니다. 서버(FastAPI)에서도 사용 권한을 검사합니다.
- 비밀번호와 비밀 설정값을 코드에 저장하거나 화면에 보여주지 않습니다.
- 실제 SQLite 데이터 파일, `.env`, `.venv`, `node_modules`, 로그와 생성 파일은 Git 기록 대상에서 제외합니다.
- Git 초기화와 커밋은 별도 요청이 있기 전까지 수행하지 않습니다.
- FastAPI와 React의 기본 기능을 우선 사용하고, 꼭 필요하지 않은 외부 패키지는 추가하지 않습니다.
- 개발과 자동 테스트는 SQLite로 진행하고, 같은 코드가 Supabase(PostgreSQL)에서도 동작하도록 한쪽 데이터베이스에서만 되는 기능은 사용하지 않습니다.

## 3. 기술 구성

| 구분 | 사용할 기술 | 역할 |
| --- | --- | --- |
| 화면 | React, Vite, React Router | 사용자가 보는 화면과 화면 이동 |
| 화면 테스트 | Vitest, React Testing Library | 화면 동작 자동 테스트 |
| 서버 | Python, FastAPI | 화면의 요청을 받아 검사·저장·조회 |
| 입력값 검사 | Pydantic | 글자 수, 형식 같은 입력 조건 검사 |
| 데이터베이스 연결 | SQLAlchemy | SQLite와 Supabase를 같은 코드로 사용 |
| 데이터베이스 구조 변경 기록 | Alembic | 표(테이블)를 만들고 바꾼 이력을 순서대로 관리 |
| 서버 테스트 | pytest | 서버 기능 자동 테스트 |
| 데이터베이스 | SQLite (개발·테스트), Supabase (실제 서비스) | 데이터 저장 |

### 3.1 서로 어떻게 연결되나요?

```text
브라우저 (React 화면)
   │  /api 로 시작하는 요청
   ▼
FastAPI 서버  ──  로그인 확인, 권한 검사, 입력값 검사
   │
   ▼
데이터베이스  ──  개발·테스트: SQLite 파일 / 실제 서비스: Supabase
```

- React 화면은 데이터베이스에 직접 접속하지 않고, 항상 FastAPI 서버를 거칩니다.
- 회원가입·로그인은 FastAPI가 직접 처리합니다. Supabase의 로그인 기능(Supabase Auth)은 사용하지 않습니다. SQLite로 테스트할 때와 Supabase를 쓸 때 로그인 방식이 같아야 하기 때문입니다.
- Supabase는 데이터베이스(PostgreSQL)로만 사용합니다.
- 로그인 상태는 브라우저가 JavaScript로 읽을 수 없는 쿠키(httpOnly 쿠키)로 유지합니다.
  - 로그인하면 서버가 추측할 수 없는 임의의 값(로그인 표)을 만들어 쿠키에 담고, 데이터베이스에는 그 값을 변환한 값만 저장합니다.
  - 로그아웃하면 데이터베이스의 로그인 표를 지워서, 쿠키가 남아 있어도 더 이상 쓸 수 없게 합니다.
  - 로그인은 마지막 로그인부터 7일 동안 유지합니다.
- 개발 중에는 React 개발 서버가 `/api` 요청을 FastAPI 서버로 전달(프록시)해서, 화면과 서버를 같은 주소처럼 사용합니다.

### 3.2 개발 서버 주소

| 구분 | 주소 |
| --- | --- |
| React 개발 서버 | `http://127.0.0.1:5173` |
| FastAPI 개발 서버 | `http://127.0.0.1:8000` |

### 3.3 환경 변수

비밀값은 `backend/.env`에 두고, 항목 이름만 `backend/.env.example`에 기록합니다.

| 이름 | 설명 | 예시 (비밀값 아님) |
| --- | --- | --- |
| `APP_ENV` | 실행 환경 | `development`, `test`, `production` |
| `DATABASE_URL` | 데이터베이스 주소 | `sqlite:///../database/buildlog.sqlite3` |

- 로그인 표를 데이터베이스에 저장하는 방식이라 쿠키 서명용 비밀값은 따로 두지 않습니다.

- Supabase 연결 주소에는 비밀번호가 들어 있으므로 `.env`에만 저장합니다.
- 화면(React) 쪽에는 비밀값을 두지 않습니다.

## 4. 예정된 프로젝트 구조

실제 개발을 시작하면 다음과 같이 역할을 나눕니다. 이름은 개발 중 임의로 바꾸지 않습니다.

```text
buildlog/
├─ backend/
│  ├─ requirements.txt
│  ├─ .env.example
│  ├─ alembic.ini
│  ├─ alembic/             # 데이터베이스 구조 변경 기록
│  ├─ app/
│  │  ├─ main.py           # FastAPI 시작점
│  │  ├─ config.py         # 환경 변수 읽기
│  │  ├─ database.py       # 데이터베이스 연결

│  │  ├─ models/           # 데이터베이스 표 정의
│  │  ├─ schemas/          # 입력·출력 형식과 입력값 검사
│  │  ├─ routers/          # 기능별 요청 처리
│  │  │  ├─ auth.py        # 회원가입, 로그인, 로그아웃
│  │  │  ├─ account.py     # 닉네임 변경
│  │  │  ├─ studies.py     # 공부 기록
│  │  │  ├─ todos.py       # 할 일
│  │  │  ├─ errors.py      # 오류 기록
│  │  │  ├─ public.py      # 공개 기록
│  │  │  ├─ comments.py    # 댓글
│  │  │  ├─ likes.py       # 좋아요
│  │  │  └─ reports.py     # 신고, 운영자 확인
│  │  └─ permissions.py    # 작성자·운영자 권한 검사
│  └─ tests/
├─ frontend/
│  ├─ package.json
│  ├─ vite.config.js
│  ├─ index.html
│  └─ src/
│     ├─ main.jsx
│     ├─ App.jsx           # 화면 이동(라우팅)
│     ├─ api/              # 서버 요청 함수
│     ├─ pages/            # 화면 단위
│     ├─ components/       # 버튼, 카드, 입력칸 같은 공통 조각
│     └─ styles/           # CSS
├─ database/
│  └─ buildlog.sqlite3     # 개발용 데이터 파일, Git 제외
└─ docs/                   # 요구사항, 동작 설명서, 개발 문서
```

## 6. Phase별 상세 계획

### Phase 0. 개발 시작 전 기준 확인

#### 목표

코드를 만들기 전에 문서, 도구, 실행 환경을 확인합니다.

#### 작업

1. `PRD.md`, `spec.md`, `plan.md`의 기능 범위가 서로 맞는지 확인합니다.
2. 첫 버전에서 만들지 않을 기능을 다시 확인합니다.
   - 이메일 확인
   - 비밀번호 찾기
   - 할 일 마감일과 중요도
   - 내 할 일 검색
   - 댓글 답글
3. 이 컴퓨터에 설치된 Python, Node.js, npm의 버전을 확인합니다.
4. 그 버전과 서로 호환되는 FastAPI, SQLAlchemy, Alembic, Pydantic, React, Vite의 안정 버전을 정합니다.
5. 비밀번호를 안전하게 저장할 방식(검증된 비밀번호 해시 라이브러리)을 정합니다.
6. 화면 코드를 JavaScript로 쓸지 TypeScript로 쓸지 정합니다.
7. 개발 서버 주소, 데이터베이스 파일 위치, 환경 변수 이름을 확정합니다.
8. 테스트 명령과 서버 실행 명령을 문서에 기록할 준비를 합니다.

#### 예상 변경 파일

- `docs/plan.md`
- 필요 시 실행 환경을 설명할 `docs/setup.md`
- 코드와 패키지는 아직 변경하지 않음

#### 확인 방법

- 세 문서를 읽었을 때 기능 범위가 충돌하지 않는지 확인합니다.
- Python, Node.js, npm 실행 여부와 버전을 읽기 전용 명령으로 확인합니다.
- 아직 패키지를 설치하거나 데이터베이스를 만들지 않았는지 확인합니다.

#### 완료 조건

- 개발 환경과 기능 범위에 막히는 항목이 없어야 합니다.
- 확인 결과를 공유하고 다음 Phase 진행 여부를 확인합니다.

---

### Phase 1. FastAPI·React 프로젝트 뼈대 만들기

#### 목표

기능 없이도 FastAPI 서버와 React 화면이 실행되고, 화면이 서버의 응답을 받아 표시하게 합니다.

#### 작업

1. `backend/.venv`에 Python 가상환경을 준비합니다.
2. FastAPI, 실행 서버(uvicorn, 자동 재시작용 watchfiles), 설정 읽기(pydantic-settings), 서버 테스트(pytest, httpx2) 패키지만 먼저 설치하고 정확한 버전을 `backend/requirements.txt`에 기록합니다. `uvicorn[standard]`는 쓰지 않습니다. (8장 참고)
3. `backend/app/main.py`에 서버 상태를 알려주는 확인용 주소(`/api/health`) 하나만 만듭니다.
4. 환경 변수를 `backend/app/config.py`에서 읽도록 하고 `backend/.env.example`에는 항목 이름만 기록합니다.
5. `frontend`에 Vite로 React 프로젝트를 만듭니다.
6. React 개발 서버가 `/api` 요청을 FastAPI 서버로 전달하도록 설정합니다.
7. React 첫 화면에서 `/api/health` 응답을 받아 "서버 연결됨"을 표시합니다.
8. SQLite 파일, 테스트·빌드 중 생성되는 파일을 `.gitignore`에 보완합니다.
9. 이 Phase에서는 아직 데이터베이스를 만들지 않습니다. 사용자 모델을 먼저 만들어야 하기 때문입니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/.env.example`
- `backend/pytest.ini`
- `backend/app/main.py`
- `backend/app/config.py`
- `backend/tests/test_health.py`
- `frontend/package.json`
- `frontend/package-lock.json`
- `frontend/vite.config.js`
- `frontend/index.html`
- `frontend/src/main.jsx`
- `frontend/src/App.jsx`
- `frontend/src/App.test.jsx`
- `frontend/src/api/health.js`
- `frontend/src/test/setup.js`
- `frontend/src/styles/base.css`
- `.gitignore`

#### 확인 방법

- FastAPI 서버가 오류 없이 시작되고 `/api/health`가 응답하는지 확인합니다.
- React 개발 서버가 오류 없이 시작되고 브라우저에 첫 화면이 보이는지 확인합니다.
- 첫 화면에 서버 응답이 표시되는지 확인합니다.
- 비밀 설정값과 SQLite 파일, `node_modules`가 Git 기록 대상에서 제외되는지 확인합니다.

#### 완료 조건

- 두 서버와 첫 화면이 정상 실행되어야 합니다.
- 사용자 모델을 만들기 전에는 데이터베이스 구조를 만들지 않습니다.

### Phase 2. 사용자 모델과 첫 데이터베이스 만들기

#### 목표

이메일로 로그인하는 사용자 구조를 가장 먼저 확정하고 첫 데이터베이스를 만듭니다.

#### 작업

1. SQLAlchemy와 Alembic을 설치하고 `requirements.txt`에 기록합니다.
2. `backend/app/database.py`에서 `DATABASE_URL`로 데이터베이스에 연결합니다.
3. 사용자 모델을 만듭니다.
4. 이메일은 필수이며 중복되지 않게 합니다. 대소문자만 다른 이메일도 같은 이메일로 봅니다.
5. 닉네임은 필수이며 중복되지 않게 합니다.
6. 닉네임은 2~20자이고 한글, 영문, 숫자, 밑줄만 허용합니다.
7. 비밀번호는 원문 대신 Phase 0에서 정한 방식으로 안전하게 처리한 값만 저장합니다.
8. 운영자인지 구분하는 값을 사용자 모델에 둡니다. 기본값은 일반 사용자이며, 화면에서 바꿀 수 없습니다.
9. Alembic으로 첫 구조 기록을 만들고 빈 SQLite 데이터베이스에 적용합니다.
10. 자동 테스트는 개발용 데이터 파일과 분리된 테스트용 SQLite 데이터베이스를 사용합니다.
11. 사용자 모델 단위 테스트를 작성합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/app/database.py`
- `backend/app/models/user.py`
- `backend/app/security.py`
- `backend/alembic.ini`
- `backend/alembic/`
- `backend/tests/conftest.py`
- `backend/tests/test_user_model.py`
- `database/buildlog.sqlite3` (Git 제외)

#### 확인 방법

- 서로 다른 이메일과 닉네임으로 사용자를 저장할 수 있는지 확인합니다.
- 같은 이메일이나 닉네임을 중복 저장할 수 없는지 확인합니다.
- 닉네임 길이와 허용 문자 검사가 동작하는지 확인합니다.
- 비밀번호 원문이 데이터베이스에 저장되지 않는지 확인합니다.
- 서버를 종료하고 다시 시작해도 사용자 데이터가 남아 있는지 확인합니다.

### Phase 4. 공부 기록·할 일·오류 기록의 데이터 구조

#### 작업

1. 공부 기록 모델을 만듭니다.
   - 작성자, 제목, 내용, 공개 여부
   - 작성 날짜·시간, 수정 날짜·시간
2. 할 일 모델을 만듭니다.
   - 작성자, 제목, 완료 여부, 공개 여부

   - 작성자, 오류 제목, 오류 내용, 해결 방법, 해결 여부, 공개 여부

9. Alembic 구조 기록을 만들고 적용합니다.
10. 데이터 모델과 상태 전환 단위 테스트를 작성합니다.

### Phase 13. Supabase 연결

#### 목표

SQLite로 완성한 기능이 실제 서비스용 데이터베이스인 Supabase에서도 똑같이 동작하게 합니다.

#### 작업

1. PostgreSQL 연결에 필요한 패키지를 설치하고 `requirements.txt`에 기록합니다.
2. 사용자가 만든 Supabase 프로젝트의 연결 주소를 `backend/.env`의 `DATABASE_URL`에 넣습니다. 연결 주소는 사용자가 직접 넣고, 문서나 코드에는 기록하지 않습니다.
3. 지금까지 만든 Alembic 구조 기록을 Supabase에 순서대로 적용합니다.
4. Supabase의 모든 BuildLog 표에 RLS(행 단위 보안)를 켜고 허용 규칙은 만들지 않습니다. FastAPI 서버만 데이터에 접근하고, Supabase의 공개 주소로는 데이터를 읽거나 쓸 수 없게 하기 위해서입니다.
5. 서버 자동 테스트를 Supabase와 같은 종류의 데이터베이스에서 한 번 실행합니다. 이때 실제 데이터와 섞이지 않도록 테스트 전용 데이터베이스나 테스트 전용 Supabase 프로젝트를 사용합니다.
6. 날짜·시간, 검색의 대소문자 처리, 중복 방지 제약이 SQLite와 같은 결과를 내는지 확인합니다.
7. 개발용 SQLite로 다시 돌아갈 때는 `DATABASE_URL`만 바꾸면 되도록 유지합니다.

#### 예상 변경 파일

- `backend/requirements.txt`
- `backend/.env.example`
- `backend/alembic/versions/` (필요한 경우 RLS 설정)
- `backend/tests/conftest.py`
- `docs/setup.md`

#### 확인 방법

- Supabase에 BuildLog의 모든 표가 만들어졌는지 확인합니다.
- Supabase에 연결한 상태에서 회원가입·로그인·기록·공개·댓글·좋아요·신고 흐름이 동작하는지 확인합니다.
- Supabase의 공개 주소로 BuildLog 표를 읽을 수 없는지 확인합니다.
- `DATABASE_URL`을 SQLite로 바꾸면 그대로 다시 동작하는지 확인합니다.
- 연결 주소와 비밀번호가 Git 기록 대상이나 문서에 들어 있지 않은지 확인합니다.

#### 완료 조건

- 같은 코드와 자동 테스트가 SQLite와 Supabase 양쪽에서 통과해야 합니다.
- 비밀값이 노출된 곳이 없어야 합니다.

### 8.4 문서 확인

- `PRD.md`, `spec.md`, `plan.md`의 기능 범위를 비교했습니다.
